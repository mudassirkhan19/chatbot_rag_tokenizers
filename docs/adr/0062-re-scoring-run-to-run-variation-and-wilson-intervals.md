# 0062. Re-scoring from the answers, run-to-run variation, and Wilson intervals on the chat report's rates

- **Date:** 2026-10-20
- **Status:** Accepted; amends [0059](0059-abstention-by-instruction-and-the-chat-report.md)'s reproducibility consequence

## Context
ADR 0059 found the pinned answer model (gemma4:e2b-mlx at temperature 0, seed 0) not run-to-run deterministic. Three separate `chat-eval` runs on one index retrieved the same Chunks and gave the same Abstentions, but 14 of the 44 replies changed wording and one grounded verdict flipped (gpt-4-number-tokens), so the grounded rate was 27 or 28 of 34. #67's criterion, "two runs give the same report apart from timings", therefore holds only for a deterministic model, as the tests' fake is.

Forcing the model to be deterministic isn't worth it. The variation comes from the runtime's numerics and caching, and one run is one sample anyway. The noise that dominates is the sample size: a 95% interval on 27/34 is about [0.63, 0.90], against the 0.03 one flipped verdict moves it. Issue #75 makes the scoring exactly reproducible, measures the model's variation, and puts intervals on the rates. It also separates a change to the scoring from model noise: #73's second lever, widening what counts as an Abstention, changes only the scoring.

## Decision
**`chat-eval --from-answers` re-scores the committed replies and rewrites the answers file.** It asks nothing and loads no index. It rebuilds every Turn from its stored question, Rewrite, retrieved Chunk ids and raw reply, and recomputes every verdict (Abstention, Citations, invalid markers, grounding, Passages found) with the current code. The stored verdicts are never read back. The answers file is rewritten with the fresh verdicts and the replies unchanged, so the stored verdicts always match the code: byte for byte when nothing in the scoring changed. Everything above the Timings section reproduces the report of the run, and the Timings section says it was not measured.

**The answers file's first line says what its Turns were asked over.** It holds the parser and chunking keys of the Chunks, and the chatbot's retriever key, k, model, revision, thinking, temperature, the sha256 of the system and rewrite prompts, and the history length. `--from-answers` refuses a file whose line differs from the current corpus and `[chat]` table, naming each field that differs. It also refuses one that names a retrieved Chunk the corpus lacks, or that doesn't ask the Evaluation set's questions in their order. The spec asked only for the Chunks' keys. The chatbot's settings are checked too because the report's Chatbot section is written from the current config: re-scoring replies a different prompt produced would put the new prompt's hash beside the old replies.

**The report names the model from the `[chat]` revision**, as `model@digest[:12] on Ollama <version>`, in a fresh run as well as a re-scored one. A run checks the live model against that revision before asking anything, so the two names are the same, and a re-scored report needs no Ollama. The tests' fake model is named by the config's pin too.

**`chat-eval --runs N` asks the whole set N times and reports run 1.** The report's Variation section gives each rate in each run with its range (abstention on the unanswerable questions and on each kind, false abstention, grounded, Recall@k), the questions whose verdict changed with their counts and verdicts in run order, and the Turns whose reply wording or retrieved Chunks changed from run 1. The answers file stays run 1. Runs 2..N are stored as full Turns, the same records with a `run` field, in a runs file beside it (`chat-answers-runs.jsonl`). So `--from-answers` rebuilds the Variation section too, and a scoring change re-scores every run. A single run removes a stale runs file. The committed report comes from N = 3.

**Every proportion has a 95% Wilson interval**: the abstention, false-abstention and grounded rates, in each row of the Results table and in the summary lines. An empty group shows `—`. The Wilson interval keeps inside [0, 1] and stays sensible at 0/n and n/n, which this report has many of (no false Abstention on 28, both out-of-topic questions abstained on). The interval covers the sampling of the questions, not the model's run-to-run variation, which the Variation section measures. **Recall@k gets no interval.** It is a mean of per-question shares, not a proportion, and it is the retriever's measure, whose paired bootstrap interval the eval report already gives (ADR 0061).

**`chat-eval --baseline <answers>` compares question by question.** It reads the baseline's answers and runs file whole before anything is written, so it may name the file the run is about to overwrite, and it works with `--from-answers`. Its verdicts are taken as stored, not re-scored: re-scoring them would erase the very scoring change being measured. A baseline asked over other Chunks or another chatbot is still compared, as a change to the prompt or the retriever is what it is for, and the section names each setting that differs. The report's *Against the baseline* section lists each question whose verdict (abstained, grounded or not grounded) differs from the baseline's run 1, marked *flaky in the baseline* when the baseline's runs disagreed on it. #73 and #72 commit their reports with this section against the committed run.

## Alternatives considered
- **Making the model deterministic**, by pinning the runtime's threads or batch size or turning off its prompt cache. The variation lives in Ollama's MLX numerics and caching, below anything the request controls, and a run that did repeat would still be one sample of 36 questions. The interval from the sample size is about ten times the variation (below).
- **Re-scoring the baseline as well.** A comparison of two re-scored files would show no change from a scoring change at all, which is the case `--baseline` is for. The stored verdicts are what the baseline's code decided.
- **Storing only runs 2..N's verdicts or replies**, not full Turns. Then a scoring change could re-score run 1 but not the variation, and the Variation section would mix old and new code.
- **An interval on Recall@k by bootstrap here.** It would duplicate the eval report's, on the same retriever and questions, and invite reading the chat report as a retriever comparison.
- **Unloading the model between runs**, so the in-process runs match separate invocations. The spec allowed it only if the in-process runs proved too stable. They did not (below).

## Consequences
- The committed run (`--runs 3`, one process) varies as ADR 0059's three separate invocations did. The retrieved Chunks were the same in all 44 Turns of the three runs, and the Abstentions were the same: no false Abstention on 28, the out-of-topic questions 2/2, the near misses 0/6. Exactly 14 of the 44 replies changed wording from run 1, as 14 did across the separate runs. One verdict flipped, gpt-4-number-tokens again (grounded in run 1, not in runs 2 and 3), so the grounded rate was 28, 27 and 27 of 34 (0.79–0.82). Ollama's prompt cache within one process doesn't make the runs more alike, so no unload is added between runs. Recall@5 was 0.41 in all three runs.
- The reported run is 28/34 grounded (0.82 [0.66, 0.92]), 26/28 on the answerable questions. A one-verdict change moves the rate by 0.03, inside an interval 0.26 wide. A later change to the prompt or the retriever should be read question by question against the baseline. A rate that moves by less than its interval, or by a question flaky in the baseline, is not an effect.
- The committed report's timings were taken while another session was embedding the corpus on the same GPU. Answering was p50 9.2 s per Turn, against 0059's 0.45 s, and the three runs took 15 minutes. The timings are the one part of the report that a rerun changes anyway.
- `--from-answers` on the full corpus takes about 1.5 minutes, nearly all of it loading the 141k Chunks and the `eval-check` gate. It needs no Ollama and no index. A scoring change, as #73's second lever is, can be measured on the committed replies with no model noise at all.
- When #70 adds a judge, its verdicts belong in the answers file, so re-scoring never calls it.
- An answers file written before this change has no first line, and `--from-answers` and `--baseline` refuse it. The committed one was rewritten by the run above.
